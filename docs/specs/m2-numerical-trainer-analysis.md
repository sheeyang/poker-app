# M2 — Numerical Trainer analysis

## Problem Statement

M1 lets a Table Owner play a continuing Cash Game against Bots through the Playground UI, with participant-safe views, durable accepted actions, and restoration. It does not yet provide the numerical analysis needed to examine a human decision against a selected Reference Strategy: its probabilities, exact sizings, selected concrete action, Decision Score, or Action Rank Score.

A human also cannot obtain reproducible Hand or Table Session averages, distinguish unfinished analysis from a complete result, or reuse an analysis that has already succeeded. Analysis must remain independent of gameplay: waiting for computation, losing a browser connection, or encountering an analysis failure must not delay acceptance of legal human actions or change poker history.

M2 must prove this complete numerical pipeline with the existing baseline Strategies. The human interprets the numbers; the application supplies no advice or good/bad judgments. Product presentation and feedback timing belong to M3.

## Solution

Extend the existing server and Playground so the Table Owner can select a complete Reference Strategy independently of Bot Playing Strategies, optionally enable Live Analysis, and inspect numerical results and analysis status. Persist those settings per Table Session. Default to UniformChoicePolicy with ProbabilitySelector and Live Analysis off.

Automatically request analysis after every accepted human decision without waiting for its completion. Use one HTTP get-or-start operation for current and historical decision analysis, an explicit failed-only Retry operation, and HTTP access to numerical results and summary averages. Reuse fully matching successful results and active jobs. Preserve successful results and their reproducibility metadata separately from authoritative poker records.

Provide backend Hand and Table Session Score Summaries over frozen sets of accepted human decisions and one fixed Reference Strategy. Return both arithmetic means only when every required analysis succeeds; otherwise report pending or error, and return no numerical score for an empty set.

Open one shared WebSocket per browser tab after identity is established. Authorize live table subscriptions individually and automatically enable a user-scoped channel for authorized analysis and summary notifications. Notifications cause relevant HTTP refreshes; initial readiness and reconnection also reconcile relevant state. Normal operation requires no polling. Use the existing bounded JobRunner with fixed numeric priorities and FIFO ordering within each priority.

## User Stories

1. As a Table Owner, I want to select a complete Reference Strategy, so that the Policy and Action Selector used for analysis are explicit.
2. As a Table Owner, I want my Reference Strategy to be independent of every Bot's Playing Strategy, so that analysis settings do not change my opponents.
3. As a Table Owner, I want the existing baseline Strategies to work throughout the numerical pipeline, so that I can validate the platform before stronger Strategies are introduced.
4. As a Table Owner, I want UniformChoicePolicy with ProbabilitySelector selected by default, so that a new Table Session has a usable analysis configuration.
5. As a Table Owner, I want Live Analysis off by default, so that pre-action numerical results appear only when I enable them.
6. As a Table Owner, I want the Reference Strategy and Live Analysis setting shared across my tabs for a Table Session, so that its configuration is consistent.
7. As a Table Owner, I want those settings restored after server restart, so that resuming a Table Session retains my choices.
8. As a human Participant, I want optional Live Analysis of my current decision, so that I can inspect its numerical Reference Strategy output before acting.
9. As a human Participant, I want each Concrete Choice's probability and exact Bet-to or Raise-to amount, so that I can inspect the Policy without losing sizing information.
10. As a human Participant, I want aggregated Action Probabilities as well as individual Concrete Choices, so that I can distinguish action-type probability from a particular sizing's probability.
11. As a human Participant, I want the Reference Strategy's selected concrete action shown separately from its Policy distribution, so that a sampled action cannot be mistaken for the entire distribution.
12. As a human Participant, I want numerical outputs without advice or good/bad labels, so that I decide what to do with the results.
13. As a human Participant, I want legal actions to remain available while analysis is pending or failed, so that computation cannot hold up my decision.
14. As a human Participant, I want every accepted decision to trigger analysis even with Live Analysis off, so that later numerical review does not depend on seeing pre-action results.
15. As a human Participant, I want analysis to begin without a feedback acknowledgement or Continue gate, so that poker progression remains independent of analysis presentation.
16. As a Table Owner, I want rejected actions and duplicate action submissions to avoid duplicate analysis work, so that retries preserve the accepted decision's identity.
17. As a human Participant, I want Decision Score calculated from my accepted concrete action and the Reference Policy, so that the score measures their numerical alignment.
18. As a human Participant, I want sized decisions compared using additional chips committed from the original decision situation, so that earlier street commitment does not distort Sizing Similarity.
19. As a human Participant, I want a legal sizing absent from the Policy distribution to remain analyzable, so that human actions are not restricted to the Policy's sampled sizes.
20. As a human Participant, I want Action Rank Score to include every legal action type and handle ties, so that omitted Policy actions and equal probabilities have defined numerical behavior.
21. As a human Participant, I want no decision scores before I have an accepted action, so that a Reference Strategy Evaluation is not confused with analysis of a decision I have made.
22. As a Table Owner, I want a matching Live Analysis evaluation reused after acting, so that scoring does not unnecessarily rerun the same Strategy.
23. As a Table Owner, I want repeated matching analysis requests to share one queued or running job, so that multiple tabs and consumers do not duplicate computation.
24. As a Table Owner, I want a successful matching result returned from cache, so that I can inspect it without another evaluation.
25. As a Table Owner, I want an existing analysis failure returned without automatic restart, so that reading results cannot silently create repeated attempts.
26. As a Table Owner, I want explicit Retry to restart only failed analyses, so that successful results and active jobs are reused.
27. As a Table Owner, I want Retry to preserve the failed request's inputs and seeds, so that it repeats the same computation.
28. As a Table Owner, I want selecting another Reference Strategy to create a separate analysis request, so that old results retain their meaning.
29. As a Table Owner, I want successful results to retain complete Strategy and reproducibility metadata, so that I can identify how each result was produced.
30. As a Table Owner, I want successful cached analysis available after server restart, so that previously completed numerical work can be reused.
31. As a Table Owner, I want a request after restart to schedule missing analysis when necessary, so that transient job state need not be durably recovered.
32. As a Table Owner, I want to analyze an authorized historical decision using the same HTTP operations, so that analysis does not require a live table subscription.
33. As a human Participant, I want historical analysis to use only information observable at the original decision, so that later reveals cannot alter its inputs.
34. As a Table Owner, I want a Hand summary containing both score averages, so that I can inspect numerical alignment across that Hand's accepted human decisions.
35. As a Table Owner, I want a Table Session summary containing both score averages, so that I can inspect alignment across its included decisions.
36. As a Table Owner, I want every decision in a summary evaluated against one selected Reference Strategy, so that the average does not mix different references.
37. As a Table Owner, I want each summary to identify its frozen decision set, captured poker revision, and decision count, so that later play cannot silently change its membership.
38. As a Table Owner, I want missing matching summary analyses scheduled in bounded batches, so that summaries can be requested without submitting unlimited work.
39. As a Table Owner, I want a complete average only after every included analysis succeeds, so that an unfinished result is never presented as a complete score.
40. As a Table Owner, I want any required failure to make the summary an error even while other work is pending, so that a failure cannot be hidden by ongoing analysis.
41. As a Table Owner, I want an empty summary to have no numerical score or analysis jobs, so that no decisions are not mistaken for zero alignment.
42. As a Table Owner, I want session averages calculated across decisions, so that Hands with different decision counts receive their correct contribution.
43. As an authenticated application user, I want one shared WebSocket in each browser tab while the app is open, so that table navigation does not replace my notification connection.
44. As a Table Owner, I want opening and closing Table Sessions to subscribe and unsubscribe on that socket, so that I receive the live table state relevant to the open views.
45. As an application user, I want each live table subscription authorized by the server, so that another user's table state cannot be exposed.
46. As a Table Owner, I want authorized analysis and summary notifications without per-table or per-analysis subscriptions, so that historical work can finish while its live table is closed.
47. As a Table Owner, I want completion and failure notifications to trigger HTTP refreshes, so that results update without polling.
48. As a Table Owner, I want a completion notification only after its result is readable, so that the resulting HTTP refresh can retrieve the successful result.
49. As a Table Owner, I want relevant analysis refreshed when the user channel first becomes ready, so that results completed before connection are recovered.
50. As a Table Owner, I want reconnect to restore live subscriptions and refresh relevant table and analysis state, so that missed messages do not leave stale results.
51. As a Table Owner, I want obsolete requests, attempts, connections, and HTTP responses prevented from replacing current state, so that delayed delivery cannot undo a newer result.
52. As a Table Owner, I want a notification received during an HTTP request to cause another reconciliation when needed, so that an earlier pending response cannot hide completion.
53. As a human Participant, I want Bot decisions and analysis to share bounded computation resources with defined priorities, so that their scheduling is predictable.
54. As a Table Owner, I want queue admission failure reported explicitly without rejecting an already accepted human action, so that resource limits remain visible and separate from poker acceptance.
55. As a Table Owner, I want a matching interactive request to reuse existing work at its submitted priority, so that requesting the same analysis does not create or reorder jobs.
56. As an engineer using the Playground UI, I want controls for Reference Strategy, Live Analysis, Retry, and summary requests with numerical results and status, so that I can validate M2 before M3 product design.
57. As an engineer, I want failed, invalid, incompatible, or timed-out analysis to leave poker records and revisions unchanged, so that the derived pipeline cannot corrupt gameplay.
58. As an engineer, I want Bot selected-action provenance preserved without adding Playing Policy distribution retention, so that M2 numerical retention remains focused on human Reference Strategy analysis.

## Implementation Decisions

- Preserve the established domain boundaries. The Poker Engine owns rules, accepted actions, and participant-safe current and historical views. Strategies owns Policy execution contracts, shared validation and canonicalization, and Action Selector execution. Research owns plain numerical scoring and arithmetic-mean calculations. The server owns authorization, orchestration, persistence, caching, request and attempt state, and scheduling. The Playground consumes safe contracts and presents results without duplicating scoring logic.
- Extend the existing modules rather than introducing a separate decision evaluator, separate Reference Strategy type, additional runner, or new connection class. Playing and Reference Strategies use the same complete Strategy descriptor. Use the existing UniformChoicePolicy, ProbabilitySelector, and HighestProbabilitySelector; stronger Policies are separate scope.
- Persist the selected complete Reference Strategy and Live Analysis setting in the Table Session's application configuration, independently of Bot assignments and the engine-owned poker record. Default to UniformChoicePolicy with ProbabilitySelector and Live Analysis off. Configuration changes follow the existing authorized, idempotent mutation path and session-revision checks; committed changes synchronize across the owner's tabs and restore after restart.
- Every durably accepted human decision triggers a nonblocking post-action analysis request regardless of the Live Analysis setting. Rejected or uncommitted actions do not become analysis targets. Duplicate accepted-action acknowledgements must not cause duplicate matching jobs. Analysis admission or execution failure cannot change an accepted poker outcome, delay acceptance while computation runs, or introduce a feedback acknowledgement gate.
- Every new analysis request captures the currently selected complete Reference Strategy and immutable participant-safe inputs for its target. Accepted human actions store no Reference Strategy assignment. A later settings change cannot rewrite an existing request or an explicit retry's inputs. Late valid historical results may populate their original cache even when play has advanced.
- Obtain historical inputs through the engine's participant-scoped historical view at the original Decision. Preserve original visibility and history boundaries even after showdown, privileged inspection, seat changes, or later Hands. Policies receive the same immutable Observable Game View shape for current and historical analysis, without authoritative game objects, connection envelopes, revisions as Policy inputs, hidden master seeds, or facts revealed only later.
- Apply the existing compatibility checks and shared Policy-result validation before consuming results. A valid Policy Result is a finite normalized distribution over legal exact Concrete Choices in canonical order. Reject incompatible Strategies, illegal or malformed distributions, and selection failures explicitly; do not manufacture fallback actions or repair invalid output outside the existing documented tolerance.
- Evaluate both parts of the Reference Strategy. A Reference Strategy Evaluation contains the validated Policy Result and the Action Selector's selected Concrete Action. The selected action does not change the distribution or the Policy-derived human scores; ProbabilitySelector may select a choice other than the largest probability.
- Cache Reference Strategy Evaluations separately from derived decision scores. Evaluation identity includes the Table Session, Participant, Hand and Decision, frozen input fingerprint, complete Policy and selector identities, implementation versions and configurations, and effective evaluation and selection seeds. Scored-result identity additionally includes the accepted human Concrete Action and scoring-method version. Reuse only fully matching entries; changes in any output-affecting identity component must not reinterpret an earlier result.
- Before action acceptance, return the Reference Strategy Evaluation without Decision Score or Action Rank Score. After acceptance, reuse a matching evaluation and calculate scores from the accepted action. Keep both stages behind the same get-or-start operation and server analysis module, including deduplication when a post-action request overlaps an in-flight evaluation.
- Persist successful cached results, including the complete Strategy descriptor, effective seeds, frozen input fingerprint, relevant versions, scoring method for scored results, target identity, and other required reproducibility metadata. Keep successful analysis separate from authoritative poker records. Reference evaluation and score retention must support matching reuse after restart. Preserve independent versioned random sources; never reveal the hidden master seed to the browser.
- Queued/running jobs and failures may remain in memory. M2 requires request-driven analysis with no durable analysis obligation, guaranteed background completion, recovery sweep, or durable event backlog. After restart, return matching successful cached results and schedule missing work when requested. A successful result must not be reported as persisted if its persistence failed.
- Provide one HTTP get-or-start decision-analysis operation: missing matching work is admitted and returns pending; queued/running matching work is reused and returns pending; successful matching work returns cached results; failed matching work returns its error without restarting. A capacity rejection is an explicit error, never pending for a job that was not admitted. Exact route names and wire-schema details remain implementation choices within these semantics.
- Provide explicit HTTP Retry for failed analysis, including failed dependencies of a summary. Retry preserves the request's frozen inputs and effective seeds, creates a distinguishable execution attempt, and reuses successful results and active jobs. Selecting a different Reference Strategy establishes a new request. Return safe structured failures rather than exposing untrusted exception details or unauthorized diagnostic information.
- The analysis module owns scheduling, cache matching, deduplication, and retry behavior. Connection modules own authentication, authorized delivery, subscriptions, and lifecycle cleanup. One consumer abandoning a shared request must not cancel work still required by another consumer.
- Calculate Decision Score as follows. Fold, Check, and Call use the matching Concrete Choice's probability, or zero if absent. For Bet or Raise, subtract the participant's pre-decision street commitment from both the human and each same-type reference total amount. Sizing Similarity is the smaller positive additional commitment divided by the larger. Decision Score is the greatest same-type Choice probability multiplied by its Sizing Similarity; no same-type choice yields zero. Legal human sizes outside the Policy's finite choices remain supported. Bet and Raise are not interchangeable.
- Calculate Action Probability by summing Concrete Choice probabilities for each legal action type. Include legal types absent from the Policy at probability zero. For Action Rank Score, order distinct aggregated probabilities from greatest to smallest; with k distinct ranks and zero-based rank i, the score is 1 minus i divided by k minus 1. Equal probabilities share a rank; when there is one distinct rank, every legal type scores one. Bet or Raise sizing does not affect its action-type rank. Probabilities and scores remain normalized numbers from zero to one; presentation formatting is separate.
- Provide backend Hand and Table Session Score Summary requests and HTTP reads of their status and both averages. Each request freezes the exact included accepted human Decision IDs, the captured poker revision, and one currently selected complete Reference Strategy for the entire set. Responses identify the summary request, its captured revision and decision count. Later decisions or configuration changes do not expand or reinterpret that request; a new snapshot requires a new request.
- Evaluate every summary member against that fixed Reference Strategy, reusing matching evaluations, scores, and active jobs and scheduling missing matches. This narrow summary-driven reanalysis is M2 scope even when earlier automatic analyses used other references. Freeze membership from committed accepted decisions; an unaccepted current decision contributes nothing. Participant-safe analysis does not require Hand completion, and summaries need no explicit session-ending lifecycle.
- Return both arithmetic means only after all required member analyses succeed. Divide the sum of each decision's score by the number of included decisions; never average Hand averages to obtain a session average. Any required failure takes precedence over pending work. Otherwise unfinished work returns pending. Neither state includes a complete numeric average, and missing or failed results contribute neither zero nor a partial average. An empty set has no numerical score and schedules no jobs.
- Retain M1's single bounded in-process JobRunner. Callers declare a typed job purpose and one central server policy assigns numeric priority: 0 for Bot decisions needed to advance play; 1 for Live Analysis and explicitly requested interactive analysis; 2 for automatic post-action analysis and missing Hand or Table Session summary analyses; 3 for future bulk Research or simulation. Priority levels use numbers, and smaller numbers dispatch first. Existing interactive completed-Hand inspection remains on the shared runner as interactive work.
- Use FIFO queues within each numeric priority, bounded running concurrency, and bounded total waiting capacity. A job's priority is fixed at submission. Matching interactive requests reuse queued/running work without changing that priority. Running work is not preempted. M2 requires no priority promotion, reserved Bot slots, additional runner, or special fairness policy; sustained arrivals at smaller priority numbers may starve other waiting work.
- Submit missing summary analyses in small batches with bounds shared globally across summary requests and browser tabs. Bound summary submissions and concurrent outstanding summary work rather than letting each request independently fill the queue. Return explicit capacity errors on admission failure. Exact batch sizes and existing runner limits are configuration/implementation details; no new throughput or guaranteed-admission target is introduced.
- Preserve M1's bounded execution lifecycle: timeout or logical cancellation does not release running capacity until the underlying computation settles. Computations receive immutable inputs and do not mutate a live Cash Game. Returning Bot work retains M1's current-decision validity checks; frozen historical analysis remains valid for its own inputs as play advances.
- Use HTTP for get-or-start, explicit Retry, result retrieval, and summary averages. Analysis WebSocket messages contain completion/failure notifications rather than numerical results. Each session-related message includes the Table Session ID; analysis and summary notifications identify the exact immutable request and execution attempt, with sufficient identity to refresh only relevant results and reject obsolete delivery.
- Persist a successful result and make it readable through HTTP before publishing completion. Record a failure before publishing its notification. A notification cannot advance either poker or session revision or be discarded merely because its gameplay revision has not changed. Summary readiness and failure must likewise be recoverable through HTTP before notifying consumers.
- Establish local identity first, then open one shared WebSocket per browser tab and retain it while the app is open. Authenticate using the existing server-issued identity cookie. Automatically enable a user-scoped channel covering analyses and summaries that user is authorized to access, with a server readiness signal independent of any live table subscription.
- Opening a Table Session subscribes to its live complete views and runtime status; closing it unsubscribes without replacing the shared socket. Authorize every subscription on the server, correlate subscription acceptance/rejection/removal with the client request, and clean up subscriptions and user-channel delivery on disconnect. Analysis and summary notifications require no per-table or per-analysis subscription. Historical analysis works with no live table subscription.
- Maintain canonical shared TypeScript message unions in Contracts, used by server and browser. TableLiveMessage permits ObservableTableUpdate with discriminator table-update, TableRuntimeStatus with table-status, and AnalysisUpdate with analysis-update. Compose these session payloads with typed user-channel readiness and table-subscription control responses in a server union; define typed subscribe/unsubscribe client messages. Do not duplicate permitted message lists locally. Exact control-message names are implementation choices.
- Once the user-scoped channel becomes ready on the initial connection, refresh relevant analysis state through HTTP to recover results completed before connection. After reconnect, restore desired live table subscriptions and refresh relevant table and analysis state through HTTP. Initial table subscriptions and resubscriptions receive the latest complete participant-safe view; missed presentation events need no replay. Normal operation performs no polling.
- Relevant completion/failure notifications trigger HTTP refresh. Guard analysis state with request and execution-attempt identity, table snapshots with session revision, and deliveries with the current connection lifecycle. Ignore obsolete requests and attempts. If a relevant notification arrives during an HTTP fetch, preserve the need to reconcile afterward so an earlier pending response cannot hide completion or failure. Disconnect and abandoned-view cleanup must not allow delayed callbacks to overwrite current state.
- Expose engineering controls and numerical results in the Playground: select the Reference Strategy, toggle Live Analysis, inspect current and accepted-decision output, see pending/error state, explicitly Retry, and request/inspect Hand and Table Session summaries. Keep legal play available throughout. Do not introduce product feedback timing, required post-action screens, advice, or good/bad labels to validate the backend.
- Preserve M1 Bot action provenance, durable mutation behavior, participant visibility, and explicit Hand starts. M2 adds successful human Reference Strategy numerical retention without retaining Bot Playing Policy distributions. Analysis cache updates, transient statuses, retries, and notifications do not add poker commands or increment poker/session revisions; committed Trainer configuration changes still follow existing session-revision semantics.

## Testing Decisions

- **Primary seam: the running application's HTTP and WebSocket boundary against real PostgreSQL.** Extend the existing server integration style rather than creating new orchestration test interfaces. Exercise authenticated users, real persistence, accepted poker actions, analysis requests, retries, result reads, notifications, summaries, restart, and shared resource contention through externally visible behavior. Reuse the existing server-construction options for controlled Strategies, bounded runner settings, and transaction fault injection. Observe evaluation inputs and invocations through controlled Strategy implementations rather than private analysis maps or queue arrays.
- A good test starts with a public action, controls only genuine external dependencies or timing, and checks the numerical result, status, durable state, authorized message, or accepted poker outcome. Do not assert private helper calls, internal container layout, exact route implementation, or UI structure. Use deterministic seeds, independently calculated expected scores, and deferred completions for reproducible races. Test polling helpers may wait for asynchronous assertions; they do not establish a polling product protocol.
- Existing Bot lifecycle tests provide prior art for held evaluations, immutable participant-safe inputs, preserved retry seeds, separate attempt identities, timeouts retaining capacity, shutdown, and late-result rejection. Existing live-transport tests provide real socket/cookie authorization, complete-view synchronization, commit-before-publication, and reconnect examples. Existing restoration, durability, recovery, and inspection tests provide real PostgreSQL restart and failure patterns. Existing Strategy tests cover canonical validation and seeded selection and should remain the authoritative baseline rather than being reimplemented.
- At the primary seam, verify the four get-or-start outcomes, simultaneous matching requests across tabs/consumers, failed-only Retry, no silent restart on read, complete cache identity, separate evaluation/score reuse before and after action, changed reference/configuration, and safe failure for incompatible, invalid, selection-failed, timed-out, capacity-rejected, and persistence-failed work. Verify successful cache and Trainer setting restoration without claiming recovery of transient obligations.
- Verify automatic analysis after accepted human actions with Live Analysis off, no scheduling for rejected actions, deduplication on accepted-action retries, no human reference assignment stored with actions, unchanged Bot provenance, and legal human/Bot progression while analysis is held or failed. Observe purpose priorities and FIFO dispatch through controlled jobs sharing the real runner; test fixed priority under an interactive match, bounded capacity, globally bounded summary submission across requests, and explicit admission error. Do not require fairness or guaranteed Bot admission.
- Verify frozen summary membership/reference/revision/count, reuse and summary-driven reanalysis, both decision-weighted arithmetic means, empty sets, pending, failure precedence, no partial averages, and failed-only Retry that preserves successful and active dependencies. Include unequal decision counts across Hands to distinguish a session mean from a mean of Hand means.
- Verify one authenticated socket can manage multiple authorized table subscriptions without replacement, unsubscribe isolation, independent user-channel readiness, cross-user access rejection, and authorized analysis notifications with no live subscription. Check result/failure readability at notification time, no numerical result payload in analysis notifications, no gameplay revision changes, and HTTP recovery after missed delivery or restart.
- **Focused numerical seam: Research's public calculation functions.** Use compact table-driven tests with independent expected values for unsized missing choices, exact and off-grid sizes, additional-commitment similarity, absent same-type choices, action aggregation, omitted legal types, tied ranks, one distinct rank, and both arithmetic means. These tests justify the reusable numerical API; no additional test-only seam is needed.
- **Browser verification: observable Playground behavior using the existing real transport fixture.** Extend its delivery controls where needed to test the client behaviors a server test cannot prove: one socket per tab across table changes, initial-ready refresh after pre-connection completion, subscription restoration, notification-triggered HTTP refresh without polling, stale request/attempt/connection rejection, and a notification racing an earlier pending HTTP response. Include a small functional check of settings, Live Analysis, nonblocking actions, Retry, and summary inspection. Reuse real HTTP/WebSocket/PostgreSQL rather than replacing the whole application with browser mocks.
- Retain the repository's existing typecheck, tests, build, and package-boundary checks. Shared message contracts must typecheck in server and Playground, and browser code must not import authoritative engine or Research implementations. Broad new engine-rule tests or duplicate Strategy-validation suites are unnecessary for this feature.

## Out of Scope

- Stronger Strategies, new poker reasoning, Solver implementation, solver-quality claims, and any claim that baseline output measures objective poker quality.
- Advice, recommendations about what action the human should take, good/bad decision labels, EV/regret scoring, separate decision evaluators, Sizing Quality, Top-Action Agreement, and Frequency Calibration metrics.
- M3 product UI, animations, final probability/score presentation design, post-action feedback timing, and when product summaries are requested or shown. M2 needs no session-ending lifecycle solely for summaries.
- M4 replay/navigation experiences, general history/reanalysis tools, counterfactual comparison, Range Visualizer, Equity / Poker Math Overlay, and overall-history summaries. Historical decision analysis and summary-driven matching reanalysis required by this spec remain included.
- Bulk Research and simulation workflows; priority 3 establishes their future scheduling purpose without implementing them.
- Durable queued/running/failure records, durable analysis obligations, guaranteed background completion, restart recovery sweeps, durable notification backlogs, distributed queues, another runner, preemption, promotion, reserved Bot slots, and starvation prevention.
- Numerical results pushed over WebSocket, normal-operation polling, per-analysis notification subscriptions, a new connection class, a new account/authentication system, and changes to M1 poker rules or accepted-command replay.
- Bot Playing Policy distribution retention and Reference Strategy assignments on accepted human actions.

## Further Notes

- This spec synthesizes the M2 design interview through Q18 and the accepted domain documentation. Later scheduling answers supersede the earlier proposal for promotion, reservations, and fairness: priorities are fixed numeric values, and matching interactive requests do not promote existing work. The final connection decision supersedes table-specific analysis delivery: one shared browser-tab socket provides authorized table subscriptions and an automatic user notification channel, with HTTP carrying analysis results.
- ADR-0026, Retain Numerical Trainer Analysis Independently of Gameplay, consolidates the M2 scope. Read it with ADR-0006, Treat Analysis as Derived Data; ADR-0008, Derive Trainer Scoring from the Reference Policy; ADR-0017, Bind Observability with ParticipantCashGame; ADR-0019, Route Computation Through One Server JobRunner; and the current six-milestone plan. Existing package, Strategy, randomness, and backend-aggregate decisions continue to apply.
- M3's intended presentation is a Hand summary after the Hand ends and a Table Session summary when the user finishes the session. This is context for later product design, not an additional M2 lifecycle or presentation requirement.
- Exact HTTP route names, control-message names, database normalization, batch constants, and supporting internal function names remain implementation choices consistent with these behaviors. This spec does not prescribe a ticket breakdown or begin implementation.
