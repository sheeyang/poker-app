# M1 — Playable engine, server, and Playground

## Problem Statement

The project currently has domain vocabulary, architecture decisions, and a milestone plan, but no runnable Poker Engine, authoritative server, Playground UI, or existing test suite. A Table Owner cannot create a Table Session, seat a human and Bots, play a complete no-limit Texas Hold'em Hand, or resume that session after a server restart.

The first playable implementation must establish trustworthy poker behavior and durable acceptance together. Illegal actions and failed persistence must not partially change cards, chips, or history; retries must not execute twice; a browser or Bot must not receive hidden information; and a restored game must reproduce the same accepted play without rerunning Strategies.

M1 delivers the complete local playable foundation described by the milestone plan and its accepted ADRs. The Playground is the enduring engineering interface through which this foundation can be exercised before the separate product experiences are built.

## Solution

Provide a locally deployed, single-user poker application backed by one authoritative Fastify server process and PostgreSQL. A server-issued local identity creates and owns continuing Table Sessions. The owner chooses human and Bot seats, configures observable cash-game settings and each Bot's Playing Strategy, explicitly starts Hands, and plays using the currently legal actions shown in a functional React Playground.

CashGame owns all Hold'em rules and automatically performs the consequences of an accepted intention: forced bets, dealing, street progression, burns, required reveals, all-in runouts, pot derivation, payouts, and completion. The server owns authorization, controller assignments, mutation ordering, revisions, idempotency, durable acceptance, recovery, and Bot orchestration. The Playground receives complete participant-safe views and displays actionable failures and recovery status.

Between Hands, the owner can manage seating, sitting out, the button, top-ups, and rebuys while preserving Participant identity and legally observable history. The next Hand always requires an explicit Start Hand operation. Restarting the server or reconnecting the browser restores the committed session rather than creating a fresh game.

Admin Mode is enabled by default for M1. Its explicit Reveal Hidden Information operation permits authorized, read-only inspection of a completed Hand, including hidden hole cards and burns where useful. It never permits active-Hand inspection, reveals the master seed to the browser, or changes an earlier participant view.

## User Stories

1. As a local application user, I want a server-issued local identity, so that I can own and resume my Table Sessions without an account system.
2. As a Table Owner, I want to create a Table Session with observable cash-game settings, so that I can choose the game I intend to exercise.
3. As a Table Owner, I want valid defaults, so that I can start with a six-seat game, blinds of 10/20, no ante, and buy-in limits of 1000 without entering every setting.
4. As a Table Owner, I want invalid settings rejected before a session becomes usable, so that impossible chip amounts or seat configurations cannot create broken games.
5. As a Table Owner, I want creation retries to return the same Table Session and participant bindings, so that a lost response cannot create duplicate games.
6. As a Table Owner, I want stable identities for my human Participant and each Bot, so that controllers, accepted actions, and observations remain associated with the correct Participant.
7. As a Table Owner, I want to choose seats and valid buy-ins for the human and Bots, so that table setup reflects the game I want to play.
8. As a Table Owner, I want each Bot to have an independently selected Playing Strategy, so that controller behavior is explicit and reproducible.
9. As a Table Owner, I want to move a Participant between Hands when seat changes are enabled, so that I can exercise different positions without changing their identity.
10. As a Table Owner, I want to make a Participant sit out or return between Hands, so that eligibility for the next Hand is deliberate.
11. As a Table Owner, I want to remove and later reseat a Participant while retaining their identity, so that cashing out and rejoining do not transfer or erase their prior observations.
12. As a Table Owner, I want to choose an eligible button seat between Hands, so that I can exercise specific positions through a normal poker command.
13. As a Table Owner, I want the button to advance past empty, sitting-out, and zero-stack seats, so that successive Hands use the documented cash-game order.
14. As a Table Owner, I want an explicit Start Hand control, so that a completed Hand never starts another Hand unexpectedly.
15. As a Table Owner, I want Start Hand rejected when fewer than two Participants are eligible, so that incomplete setup cannot begin a Hand.
16. As a Participant, I want correct heads-up and multiway blinds, dealing, and action order, so that position behaves consistently with the documented rules.
17. As a Participant, I want antes and short forced contributions handled correctly, so that an all-in from an ante or blind remains part of the Hand.
18. As a Participant, I want to see my own hole cards and currently public information, so that I can decide without access to opponents' unrevealed cards or future cards.
19. As a Participant, I want my visible legal actions to match what CashGame accepts, so that the Playground does not suggest an action the rules reject for the same snapshot.
20. As a Participant, I want to Fold, Check, or Call when legal, so that I can make every unsized poker decision.
21. As a Participant, I want to submit any legal integer Bet-to or Raise-to amount, so that human play is not restricted to the baseline Policy's selected sizes.
22. As a Participant, I want sizing controls to show total commitment on the current street, so that I understand the meaning of a bet or raise amount.
23. As a Participant, I want a short all-in represented as an ordinary legal Bet, Raise, or Call, so that the action contract remains consistent.
24. As a Participant, I want minimum raises and cumulative short-all-in reopening applied correctly, so that my right to raise follows the amount I face and my prior action.
25. As a Participant, I want wrong-turn, stale, and illegal submissions rejected clearly, so that I can refresh or correct the decision without corrupting the Hand.
26. As a Participant, I want street transitions, burns, and board deals to follow automatically from accepted actions, so that I do not need to control dealer mechanics.
27. As a Participant, I want required live hands revealed before an automatic all-in runout, so that the visible game follows the documented showdown behavior.
28. As a Participant, I want a Hand won by folds to settle without exposing the winner's hole cards, so that unrevealed cards remain private.
29. As a Participant, I want main pots, side pots, returned unmatched excess, split pots, and odd chips settled correctly, so that each Participant receives only the chips they are entitled to win.
30. As a Participant, I want complete stacks and pot information after settlement, so that I can understand the result of a Hand.
31. As a Table Owner, I want to top up to a target stack between Hands, so that I can add chips without confusing the target with an increment.
32. As a Table Owner, I want a zero-stack Participant to rebuy within the buy-in limits, so that they can become eligible for another Hand.
33. As a Participant, I want to continue with a positive stack below the minimum buy-in, so that losing chips does not force an unnecessary rebuy.
34. As a Table Owner, I want active-Hand seating and external stack changes rejected, so that the participating seats and contributions remain fixed for the deal.
35. As a Participant, I want Bot thinking and failure status visible, so that I understand why the game is awaiting a Bot decision.
36. As a Table Owner, I want to retry failed Bot work or explicitly change its Playing Strategy, so that I can recover without an implicit fallback poker action.
37. As a Participant, I want my legal human actions available independently of unrelated computation, so that the interface remains responsive.
38. As a Participant, I want late or obsolete Bot results discarded, so that a previous decision or controller assignment cannot act in the current game.
39. As a Table Owner, I want accepted Bot actions to retain their original Strategy and randomness provenance, so that later controller changes do not erase how an action was chosen.
40. As a Participant, I want a complete latest view on reconnect, so that losing WebSocket updates cannot leave my cards, stacks, or actor out of sync.
41. As a Participant, I want duplicate and out-of-order updates ignored, so that old data or repeated presentation events cannot overwrite the current session.
42. As a Table Owner, I want server restarts to restore poker state, controllers, and committed revisions, so that the same Table Session continues from its durable history.
43. As a Table Owner, I want a retried mutation to return its original definitive acknowledgement or rejection, so that network retries do not reinterpret the attempt against a later state.
44. As a Table Owner, I want reuse of a requestId with different contents rejected, so that one logical attempt cannot silently become another.
45. As a Participant, I want uncommitted changes withheld from gameplay updates, so that everything I see as accepted corresponds to durable state.
46. As a Table Owner, I want recovery to pause an affected session while a commit outcome is unknown, so that further play cannot race an unresolved transaction.
47. As an authorized Admin Mode user, I want to inspect hidden information for a completed Hand explicitly, so that I can validate dealing, burns, and payouts.
48. As a Participant, I want active-Hand hidden information protected even in Admin Mode, so that privileged inspection cannot influence live decisions.
49. As a Participant, I want later reveals to leave my earlier decision views unchanged, so that historical observations represent what I actually knew.
50. As a developer, I want a reusable engine with atomic high-level commands, so that gameplay and later Research, Solver, and simulation workflows share one rules implementation.
51. As a developer, I want deterministic accepted-command replay and complete restoration, so that a seed and successful intentions reproduce the same domain facts and identifiers.
52. As a developer, I want detached records, immutable observations, and independent forks, so that a consumer or failed working operation cannot mutate committed state indirectly.
53. As a developer, I want versioned independent deck, Policy, and selection randomness, so that changing one subsystem's random consumption does not change another's outcomes.
54. As a developer, I want shared Policy-result validation and canonicalization, so that every Bot uses the same legal normalized distribution and deterministic ordering.
55. As a developer, I want the Playground maintained as a separate engineering interface, so that platform validation does not dictate the later Trainer or Research Lab experience.
56. As a developer, I want behavioral tests at the public engine and server boundaries, so that correctness survives internal refactoring and database failures.

## Implementation Decisions

- **Workspace and dependency boundaries.** Establish a pnpm workspace with distinct Contracts, Engine, Strategies, Solver, Simulation, and Research packages, plus Server and Playground applications. Solver and Simulation need only their architectural boundaries in M1, not implementations of later milestones. The Engine depends on neither Strategies nor Research. Research is server-only and may consume the engine and other server-side capabilities; those packages do not depend back on Research. Browser applications import only safe wire contracts and browser-safe dependencies, never authoritative engine or Research implementations. The product Web application is deferred to M3 under the current six-milestone plan.
- **Local runnable stack.** Use Node.js/Fastify, PostgreSQL/Drizzle, and the documented React/Vite, TanStack Router, TanStack Query, Zustand, and Tailwind browser stack. Provide reproducible local database initialization and commands for starting the server and Playground and running checks. Correctness takes priority over optimization. This milestone uses one local application user and one backend process.
- **Configuration.** Keep explicit Observable and Hidden Game Configuration types and construct runtime projections field by field. Validate seat capacity as an integer from 2 through 9; default it to 6. Defaults are small blind 10, big blind 20, equal per-player ante 0, and minimum/default/maximum buy-in 1000. Validate representable integer chip amounts, a positive small blind, big blind at least small blind, nonnegative ante, and ordered buy-in limits independently of occupancy. The initial button defaults to seat 1 and resolves clockwise to an eligible seat. M1 uses seat changes enabled by default; an explicitly disabled policy rejects movement. Configuration is immutable for a Table Session; different settings or a fresh game require a new session. There is no Reset Table operation.
- **Identity, ownership, and bootstrap.** Use a server-issued opaque HttpOnly cookie for local application identity. The authenticated creator is the Table Owner. Allocate stable ParticipantIds for the human and configured Bots and persist human-user bindings and Bot controllers in the backend aggregate. Only the owner manages the table and controllers; human action authorization additionally checks the user's binding to the acting Participant. A client-supplied ParticipantId, seat, or observer binding does not establish permission. Participant/controller allocation is application data; seating, buy-ins, and button setup use the same accepted CashGame commands as later changes.
- **Hidden master seed.** The server generates and retains the master seed and supplies complete configuration to trusted engine construction. Normal creation accepts observable game settings and rejects hidden game configuration, including a client-provided seed. Controller/bootstrap intentions are validated application data, never an alternative authoritative poker state. Master seeds are absent from ordinary HTTP responses, WebSocket updates, participant views, presentation events, Policy inputs, and privileged browser inspection results. Tests and trusted internal tooling can construct the same engine with known explicit seeds.
- **One semantic state owner.** CashGame is the deep stateful no-limit Texas Hold'em module, with one private plain-data representation covering participants, seats, table facts, cards/deck, contributions, stacks, and betting state. Focused internal helpers implement cards/dealing, betting, bookkeeping, derived pots, settlement, hand ranking, and visibility without creating a second state owner, generic PokerCore, or rules-profile hierarchy. Public callers never orchestrate low-level dealer mechanics.
- **Public commands and atomicity.** Expose creation, record export/restoration, independent forking, and the high-level commands seatParticipant, leaveParticipant, moveParticipant, setSittingOut, topUpTo, setButton, startHand, and act. Each mutation computes its entire transition on an isolated draft, validates invariants, and commits the next state and one accepted command together. A structured expected rejection or unexpected defect leaves live state and accepted history unchanged. Return structured domain rejections for expected failures; reserve exceptions for defects or broken invariants. Events describe the complete accepted transition but are not a second authoritative record.
- **Participant continuity and readiness.** Eligibility requires being seated, not sitting out, and having at least one chip before forced contributions; starting requires at least two eligible Participants. Freeze participants and seats for the active Hand. Reject table-membership, seat, button, sitting-out, and external stack mutations during an active Hand. Movement, leaving, rebuying, and rejoining preserve ParticipantId. Button advancement is clockwise from the previous button seat, even if its occupant leaves, skipping ineligible seats. An explicit eligible between-Hand button selection overrides the next position. A seat never owns identity or observations.
- **External chip changes.** Joining uses a buy-in within inclusive limits or the configured default. topUpTo means the desired resulting stack, must increase it, and cannot exceed maximumBuyIn. A zero-stack rebuy must reach minimumBuyIn; a positive-stack top-up may remain below it. Positive stacks below the minimum remain eligible. Seated Participants cannot lower their stacks or withdraw chips without leaving. Track accepted buy-ins, top-ups, and cash-outs so conservation accounts explicitly for chips entering and leaving the Cash Game.
- **Forced bets, turns, and dealing.** Apply equal per-player antes before blinds, each capped by remaining chips; antes do not count toward the preflop street wager. Determine seats/button/blinds before collecting contributions. Follow the documented heads-up and multiway blind positions, preflop/postflop action order, and two clockwise hole-card passes. Use one deterministic standard 52-card deck. Burn before the flop, turn, and river, dealing 3/1/1 board cards; automatic runouts use that same sequence. Do not deal or burn unused future streets after an early completion. Folded and all-in Participants receive no betting turns.
- **Legal actions and reopening.** One internal legality calculation powers both observable descriptions and current-state act validation. Check requires nothing owed; Call is capped by the stack. Bet-to and Raise-to are exact integer total street commitments, and every legal integer size is accepted. Full opening bets use the big blind minimum; full raises use the last full bet/raise increment. Below-minimum sizes are legal only as genuine all-ins. Track prior action and participant-specific reopening, including cumulative short-all-in increases reaching the applicable full-raise threshold. Expose inclusive sizing bounds or one permitted short-all-in size, never inverted bounds or an enumeration of all chip amounts. All-in is an ordinary Bet, Raise, or Call, not a separate action.
- **Automatic progression and settlement.** startHand includes forced bets, shuffle, deal, and first actor in one transition. act includes every resulting round closure, street wager reset, burn/deal, next actor, reveal, runout, return, payout, and completion. Close betting only after all required live decisions and matching commitments are satisfied. Resolve outstanding Call/Fold decisions before deciding that no further betting is possible. Reveal all remaining live hands when betting becomes impossible or at a multi-hand river showdown. A lone live hand wins immediately without exposing its hole cards.
- **Ranking and pots.** Evaluate the best five-card rank from the two hole cards and five board cards, including complete kickers, ace-low straights, and suit-independent ties. Derive pots from contribution layers rather than a second mutable pot balance; folded contributions remain but folded Participants lose eligibility. Return unmatched excess rather than making a one-Participant side pot. Settle each pot independently among eligible hands, split ties in integer units, and award odd chips clockwise from the button among tied winners independently per pot. For example, contributions 100/300/300 produce pots of 300 and 400; 100/300 produce a matched pot of 200 and a return of 200.
- **Participant projections.** ParticipantCashGame is a lightweight, short-lived facade bound to one CashGame instance and stable ParticipantId. Its primary getView returns one immutable Observable Game View containing configuration, state, and participant-specific history; projectEvents separately constructs safe presentation events. Obtain fresh facades from the latest committed game. Do not retain live facades in asynchronous work or add duplicate decision-state types or separate convenience reads without a concrete need. Physically omit hidden data at runtime rather than narrowing an authoritative object's TypeScript type.
- **Historical visibility.** Support participant views at an engine-owned DecisionId using the information legally observable at that point. Observable Session History begins when the Participant joins and includes only information they could observe; absence and rejoining cannot invent missed information. Movement preserves history and a new seat occupant does not inherit it. Later showdown or Admin Mode reveals never retroactively reveal earlier hidden facts. Bots and Policies receive only these immutable participant-safe snapshots, including legal-action descriptions when they are the actor.
- **Poker record and restoration.** Export detached immutable version-1 Table Session Records containing schemaVersion, engineVersion, complete authoritative configuration, and ordered successful high-level commands, including initial setup. Do not separately persist decks, derived Hand seeds, burn identities, card traces, RNG state, private live state, rejected commands, or CashGame events as replay authorities. fromRecord validates format and supported versions, reconstructs a temporary game through normal commands, checks complete invariants, and returns either a complete usable reconstruction or a structured failure. A malformed or rejected suffix must never expose a usable prefix. Restoration reproduces domain identifiers, cards, stacks, contributions, pots, button, actor, street, histories, and regenerated events. A fork is independent, preserves deterministic continuation and history, records no mutation, and shares no mutable state.
- **Backend aggregate and durable schema.** Persist a logical aggregate comprising the engine poker record, Table Ownership, participant/user/controller bindings, controller Strategy assignments/configuration, version metadata, and committed pokerRevision and sessionRevision. Preserve an application-owned location for future Trainer configuration without implementing Trainer preferences or analysis UI in M1. Persist processed mutation outcomes and accepted Bot-action provenance alongside their corresponding durable commands. PostgreSQL normalization is an implementation choice; the aggregate and its transactional guarantees are the contract. Initial formats are version 1; pre-release changes may break records without migrations or old-version replay support.
- **Revision ownership and request contracts.** CashGame owns HandId and DecisionId but no concurrency revision. The backend owns requestId, request fingerprints, both revisions, and expected-revision checks. Poker mutations carry expectedPokerRevision; controller/application configuration mutations carry expectedSessionRevision. A committed successful public poker mutation advances both counters once; a committed application configuration change advances sessionRevision only. Rejections, duplicates, confirmed rollbacks, derived data, and transient presence/controller statuses advance neither. Keep revisions outside engine methods, records, Observable Game Views, and Policy inputs.
- **Mutation ordering and durability.** One FIFO queue per Table Session serializes requests in the single backend process; other sessions may proceed concurrently. Resolve committed request identity before checking the expected revision. For a fresh poker attempt, check its expected revision, fork the committed CashGame, execute the command, and atomically commit the accepted command, revisions, relevant Bot provenance, and processed request outcome. Promote the working game and revisions together and publish updates only after confirmed commit. Discard a rejected or confirmed-rolled-back working copy. Application configuration changes use the same serialized aggregate acceptance discipline without fabricating poker commands.
- **Definitive outcomes and fingerprints.** Store a small acknowledgement or structured definitive rejection with a canonical fingerprint of the logical request, including its operation, payload, expected revision, and authenticated scope as applicable. A matching requestId retry returns the stored outcome without re-execution, even if state has since advanced; changed contents reject reuse. Domain and application rejections are persisted outside the poker command record. Infrastructure errors without a committed definitive outcome are distinct from stored rejections. Do not save complete observable views as idempotent responses; synchronize the current view separately. Enforce unique table/request identities in PostgreSQL. Creation uses authenticated user/requestId identity and atomically persists the new aggregate and creation outcome, preserving the same TableSessionId, master seed, and bindings on a matching retry.
- **Unknown-commit recovery.** Losing COMMIT confirmation is not a rollback. Put the affected Table Session into recovery and pause its mutation queue and Bot submissions until the database outcome is resolved and the confirmed aggregate is reloaded. An initially absent processed-request row cannot establish noncommit while the transaction is unresolved. Return a stored outcome when committed; after confirmed noncommit, do not automatically re-execute the attempt. A human may submit a new requestId, or Bot orchestration may freshly evaluate the still-current decision. Apply equivalent outcome resolution to creation before permitting duplicate creation.
- **HTTP and WebSocket synchronization.** Expose safe requests for session creation/read, owner table/controller management, human actions, Bot retry, subscription, and authorized completed-Hand inspection. Use structured success/rejection/error contracts. Authorize the observer independently of any supplied identifier. Every committed WebSocket update carries TableSessionId, both committed revisions, a complete Observable Game View, and optional safe presentation events describing that same committed aggregate. Order by sessionRevision; clients ignore older/already-processed updates and can accept a newer full view despite a gap. Reconnection supplies the current full view without requiring missed events. Burn events contain no card identity; raw engine events stay server-side.
- **Strategy contract and baseline.** A Strategy composes a logically stateless Policy and an Action Selector. Policies evaluate the immutable Observable Game View directly, with declared configuration and separate execution options, and may return synchronously or asynchronously. checkCompatibility consumes that same view and returns structured unsupported reasons before evaluation. Strategies own no persistent cross-Hand memory; adaptive Policies can derive information from Observable Session History. UniformChoicePolicy assigns equal probability to legal unsized choices and the minimum/maximum legal sized choices, deduplicating coincident sizes and including one short-all-in size once. Compose it with ProbabilitySelector by default and also expose HighestProbabilitySelector. This baseline makes no claim of poker expertise.
- **Shared validation and canonical order.** One Strategies-owned validator checks a nonempty finite legal distribution, finite probabilities in [0,1], at least one positive entry, exact legal integer sizes, duplicate concrete actions, and probability sum against the frozen view. Invalid outputs are explicit failures, never repaired or replaced with fallback actions. Return a new immutable Policy Result preserving informational diagnostics, omit zero-probability entries, and normalize only sum drift within tolerance. For M1, define canonical order as Fold, Check, Call, Bet by increasing betTo, then Raise by increasing raiseTo; use absolute probability-sum tolerance 1e-9 and document it. These fill details explicitly left open by ADR-0009. Selectors consume the unchanged canonical distribution without sorting or additional strategic reasoning. HighestProbabilitySelector keeps the first greatest-probability choice, replacing it only for a strictly greater probability and consuming no seed.
- **Independent versioned randomness.** Derive deck, Policy, and selection seeds directly from the hidden master seed plus separate namespaces and stable Hand/Participant/Decision identities, never by sequential consumption of one shared RNG. Explicitly define and version derivation input encoding, derivation algorithm, deterministic random generation, range sampling, and shuffle before treating v1 records as complete, and lock them with reproducible fixtures. Supply only each job's effective seed and declared inputs. Given matching implementation/version, configuration, inputs, and effective seeds, reproduce the Policy distribution and selected action; forbid undeclared random calls, wall-clock decisions, or mutable external dependencies affecting output. Strategy configuration declares every output-affecting parameter, rather than a universal computationBudget.
- **JobRunner and Bot orchestration.** All M1 Policy computation uses one server-managed JobRunner for execution, bounded concurrency, cancellation, timeouts, and explicit failures. Jobs receive immutable participant-safe snapshots and declared configuration/seeds, return plain results, and cannot mutate a live authoritative game. Capture pokerRevision and evaluation identity in orchestration metadata, outside Policy inputs. Returned Bot work re-enters the session queue and checks captured pokerRevision, ParticipantId, DecisionId, current Strategy assignment/version/configuration, effective seeds, and evaluation request identity before submitting a normal act command. Cancellation is optional efficiency; these validity checks are required correctness. Invalid, incompatible, failed, timed-out, or obsolete work submits no poker action and advances no revision.
- **Bot failure and provenance.** Show thinking or structured failure in the Playground. Retry the unchanged decision from the same declared inputs/seeds, or let the owner explicitly replace the Strategy and initiate current work. Do not call, fold, or choose another implicit fallback. Accepted Bot commands retain Policy and selector identities, versions, configurations, and effective seeds or reconstructible provenance in application data committed with the action. Restore accepted actions directly without rerunning Strategies, then resume required Bot work for the current decision. Bots may continue an active Hand while a browser is disconnected; a human decision waits without inventing an action.
- **Completed-Hand inspection.** Research reconstructs a trusted CashGame from durable poker inputs and reads immutable completed-Hand facts through authoritative engine APIs. Inspection runs through JobRunner and returns a purpose-built DTO. The server enforces local identity/Table Ownership, Admin Mode, and requested-Hand completion, including direct requests bypassing the UI. Admin Mode is on by default; disabling it removes backend access as well as the control. Authorized results may include all hole cards, burns, reconstructed deck order, or deal trace where useful, but omit the master seed and unrestricted live objects. Reveal is read-only and cannot alter poker commands, revisions, historical projections, or Policy inputs.
- **Functional Playground.** Build an independent React engineering interface exposing creation/configuration, human/Bot seats and controllers, the public between-Hand operations, explicit Hand start, safe current cards/stacks/pots/street/actor, legal action controls including exact Bet-to/Raise-to amounts, target-stack top-up/rebuy, Bot retry/Strategy changes, reconnect and mutation/recovery feedback, and authorized completed-Hand reveal. Keep the latest complete server view as the gameplay truth. Present committed acknowledgements, stored rejections, stale-state refresh, and pending infrastructure/recovery outcomes distinctly. A completed-Hand selector sufficient for inspection is included; action-by-action history/replay product tooling is deferred. Animation and polished product UX are not completion criteria.

## Testing Decisions

- **Primary seams.** Use two principal behavioral boundaries: the public CashGame/ParticipantCashGame API for comprehensive poker, projection, and replay tests; and the real Fastify HTTP/WebSocket boundary backed by a real isolated PostgreSQL database for authorization, aggregate acceptance, Bot execution, and recovery tests. Add a small browser smoke flow for Playground wiring. There is no existing implementation or test prior art; the accepted ADRs and M1 completion criteria supply the behavioral fixtures. Do not create a generic low-level PokerCore or expose private state solely for testing.
- **Good tests.** Drive high-level intentions and assert observable views, accepted records, immutable facts, public results, durable outcomes, and published wire payloads. Avoid private draft layouts, helper call counts, rendering structure snapshots, or tests that merely mirror implementation. Use explicit known trusted seeds and configured game inputs, with reproducible command sequences and independently stated expected results. Add focused public Strategy validator/selector or pure hand-ranking tests only where they efficiently establish exported contract behavior beyond the integration fixtures; avoid duplicating the whole pipeline at each internal layer.
- **Configuration, seating, and chip flow.** Cover defaults; invalid integers/ranges/limits; valid empty configuration versus Hand readiness; two- and nine-seat boundaries; unique seats and identities; sitting out; button advancement/override; prohibited active-Hand changes; seat-change policy; leave/rejoin history; positive stacks below minimum; target-stack top-ups; zero-stack rebuys; cash-outs; and rejection without state/history changes. Track chips in stacks and contributions against explicit external inflows/outflows after every accepted command.
- **Betting and progression.** Exercise heads-up and multiway positions; ante versus street wagers; short antes/blinds; checks/calls; minimum and maximum sizes; arbitrary interior integer sizes; genuine below-minimum all-ins; wrong actors; insufficient raises; closed versus reopened action after one or cumulative short all-ins; outstanding calls before automatic runout; automatic street closure; completion by folds; and showdown. Confirm displayed legality and actual acceptance agree at the same snapshot, including a single short-all-in size.
- **Cards, ranking, and payouts.** Verify deterministic shuffle/deal order, unique card locations, burn-before-3/1/1 dealing, identical all-in runout sequence, and absence of unnecessary future burns/deals. Use independent expected ranking fixtures for every category, kickers, board-playing ties, the wheel, invalid wraparound, and no suit tiebreak. Cover layered main/side pots, folded contributions, differing caps, returned unmatched excess, tied winners, odd chips per pot, and exact conservation through settlement; include the 100/300/300 and 100/300 examples.
- **Atomic engine failure, forks, and records.** Assert successful commands append exactly once and rejected commands append nothing. Trigger controlled failures through a narrow internal test harness when necessary to establish that exceptions during a transition also preserve the full public before-state and record; do not add public mutation escape hatches. Mutate/further play independent forks and confirm the source is unchanged. Exported records and snapshots must not permit alias mutation. Round-trip multi-Hand records and compare domain facts, historical/current participant views, identifiers, regenerated events, and subsequent deterministic continuation. Reject malformed versions, configuration, or commands anywhere in a record without returning a usable prefix.
- **Information boundaries.** Inspect actual serialized HTTP and WebSocket data and Policy job inputs, not just their static types. Prove absence of master seeds, unrevealed opponent cards, future cards, deck order, and burn identities on normal paths. Verify own cards, required public reveals, fold-win privacy, join-time/history restrictions, movement/rejoining, and unchanged earlier decision snapshots after showdown or privileged inspection. Reject unauthorized observer/actor/management requests, Admin Mode disabled access, and active-Hand reveal even through direct endpoints. Completed-Hand inspection must omit seeds and leave record/revisions unchanged.
- **Strategy and JobRunner behavior.** Verify UniformChoicePolicy coverage, equal probabilities, endpoint-size deduplication, and the single short-all-in case. Feed unordered equivalent distributions through the real execution pipeline and assert canonical identical results; cover duplicates, illegal sizes, empty/all-zero results, nonfinite/out-of-range probabilities, sum drift within and beyond 1e-9, zero omission, and immutable diagnostics-preserving output. Verify first-canonical-choice highest-probability ties and seeded sampling without changing probabilities. Lock independent derivation/shuffle fixtures and prove Policy/selector random consumption cannot change decks. Exercise compatibility failures, timeouts, retries, assignment replacement, obsolete queued results, and restart resumption; no failure may submit a fallback command. Accepted Bot provenance must survive later configuration changes, and restoration must not reevaluate historical Bot actions.
- **Durable mutation integration.** Use the real database transaction path and actual published updates. Verify FIFO acceptance, correct revision increments, expected-revision rejection, matching success/rejection retries after subsequent play, conflicting requestId reuse, unique request identities, atomic creation retries, and separate application-only changes. Hold or fail persistence before commit and confirm neither committed cache nor subscribers expose the working state. Force confirmed rollback and verify no command/revision promotion. Model lost COMMIT acknowledgement for both eventual commit and confirmed noncommit, including an initially absent outcome while resolution is pending; assert recovery pauses mutation/Bot submissions, loads confirmed state, and never automatically re-executes confirmed noncommit. A fault-capable persistence adapter may control timing/errors, but it must wrap the real transaction path rather than replace PostgreSQL with an in-memory imitation.
- **Restart and synchronization.** Restart the server against committed database contents and assert the same poker facts, participant/controller bindings, Bot provenance, and both revisions. Reconnect over WebSocket and verify a complete view; ignore duplicate/older updates, accept newer views across gaps, and avoid replaying duplicate presentation events. Verify human decisions wait during disconnection, Bots can continue the active Hand, and completion never automatically starts the next Hand.
- **Playground smoke and completion gate.** Through the browser, create a configured table, place a human and baseline Bots, start a Hand, use a legal action including a sized action in a controlled fixture, reach settlement, top up/rebuy when applicable, inspect an authorized completed Hand, and reconnect to current state. Verify visible Bot failure/retry and structured stale/recovery feedback in targeted scenarios. Complete workspace type/build checks and dependency-boundary checks that keep authoritative packages out of the browser. M1 is complete only when the full playable vertical slice and all rule, information, replay, and durability criteria pass together.

## Out of Scope

- Trainer recommendations, Reference Strategy selection UI, Live Analysis, Decision Score, Action Rank Score, and retained derived-analysis results/caches (M2).
- The main product Web interface, polished product UX, dealing/burn animations, and animation-driven flows (M3). Safe presentation-event contracts are included now.
- Product hand history, action-by-action replay tooling, reanalysis, counterfactual Strategy comparison, Range Visualizer, Equity / Poker Math Overlay, and deeper Research tools (M4). Engine reconstruction, historical participant projections, and authorized completed-Hand inspection are included now.
- A concrete Solver, language-neutral Solver execution implementation, hypothetical scenario construction, or a shared transition-kernel extraction (M5).
- Automated successive-Hand simulation runs, mass simulation, benchmarking, Research Lab comparisons, throughput targets, and non-trivial performance optimization (M6).
- Accounts, publication/deployment beyond local development, online multiplayer, multiple server processes, distributed mutation coordination, and database row locking for multi-server operation.
- Other poker variants, tournaments, separate rules profiles, alternative ante structures, straddles, missed-blind debt, seat-change penalties, optional showing/mucking, rabbit hunting, dealer corrections, and other alternative live-poker procedures.
- Persistent Strategy memory, manual Action Selectors, browser-authoritative poker, unrestricted live inspection, persisted engine snapshots/event histories, Reset Table, backward compatibility guarantees, migrations for pre-release record-breaking changes, or version-specific old-engine replay implementations.
