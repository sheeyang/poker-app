# Use a Hold'em-Specific CashGame with One State Owner

The engine will expose a deep stateful CashGame module specialized for No-Limit Texas Hold'em, without a separate generic PokerCore abstraction. CashGame owns the complete authoritative game state and rules; reuse across gameplay, Research, simulation, and Solver workflows is a concrete requirement, while a cross-variant hierarchy is not. This replaces the earlier decision to split rules and mechanical state between CashGame and PokerCore.

CashGame has one private plain-data state representation containing table and Hand data, including participants, seats, cards/deck, stacks, contributions, and betting state. Focused internal modules handle cards/dealing, betting, contribution bookkeeping, derived pots, settlement, hand ranking, and visibility without independently owning competing mutable copies of that state. They may use pure calculations and controlled draft mutation; the public interface remains stateful, so callers submit intentions such as `startHand()` and `act(...)` rather than passing or replacing internal state.

Every public mutation computes its complete transition on an isolated draft of the whole state, validates rules and invariants, and commits the resulting state and accepted command together. Rejection or failure discards the draft. Internal helpers preserve card uniqueness, valid chip amounts, contribution consistency, and chip conservation; separating those helpers for testing does not create another game abstraction or permit callers to orchestrate low-level mechanics. The agreed cash-game behavior remains in [ADR-0025](0025-document-standard-cash-game-rules.md).

The engine may expose its pure Texas Hold'em hand-ranking helper to trusted server-side consumers so Research equity calculations reuse the same ranking implementation as CashGame settlement. The helper evaluates explicitly supplied cards without reading private game state; dealing, visibility, and payout decisions remain CashGame responsibilities. ParticipantCashGame remains a distinct participant-safe projection facade, not another authoritative state owner.

For the current milestones, gameplay, simulation, and Solver workflows reuse this same CashGame implementation for all Hold'em rules and progression. Do not introduce a separate Solver rules implementation now. A later milestone may extract a shared Hold'em transition kernel from CashGame for both CashGame and the Solver, but that is a future extraction rather than an additional current abstraction; see [ADR-0004](0004-use-a-language-neutral-solver-boundary.md).
