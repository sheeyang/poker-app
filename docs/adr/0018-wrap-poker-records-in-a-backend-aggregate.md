# Wrap Poker Records in a Backend-Owned Aggregate

The backend will persist each Table Session as a logical PersistedTableSession aggregate containing the engine-owned TableSessionRecord plus participant controllers and Trainer configuration, independently of how PostgreSQL normalizes it. CashGame restores only the nested poker record and remains unaware of Bots, Strategies, preferences, or database infrastructure; recorded Bot actions replay as accepted poker commands without rerunning Strategies. This preserves a reusable engine while retaining the application state required to resume a session after restart.

A Bot Strategy failure remains an application-level controller outcome and submits no poker command or implicit fallback. The unchanged decision may be retried with the same declared inputs and derived seed, or the Table Owner may explicitly replace the Strategy before evaluation resumes.

The backend owns both `pokerRevision` and `sessionRevision` as durable metadata in the PersistedTableSession aggregate, outside the engine-owned TableSessionRecord. `pokerRevision` advances once for each durably committed successful public poker mutation, represented by one accepted CashGameCommand. `sessionRevision` advances on committed poker or application configuration changes to the aggregate. A rejected mutation, confirmed persistence rollback, duplicate request returning an existing outcome, derived cache update, or transient controller or presence status advances neither revision.

Poker requests use `expectedPokerRevision` for the poker revision; application configuration requests use `expectedSessionRevision`. The explicit names distinguish the two server-side concurrency checks. Both expectations and requestId are backend request metadata, not CashGame arguments or part of TableSessionRecord. CashGame owns poker behavior, accepted commands, and domain identifiers, but no concurrency revision counter. Keeping both counters in the server places stale-request checks, Bot-result validation, synchronization, and durable acceptance together; the server's centralized mutation path must consistently advance revisions for every committed mutation.

Restoration reconstructs CashGame from the nested poker record and loads both committed revision values from the backend aggregate. The cached game and its server revision metadata are promoted or replaced together, without injecting revisions into CashGame. HandId and DecisionId remain engine-owned, deterministic domain identifiers independent of these counters.

Browser disconnection and server restart do not themselves submit poker commands. Bots may continue the current Hand while human decisions wait for reconnection; restoration replays the poker record, restores controllers, and restarts any required Bot work from immutable participant-safe inputs. Normal gameplay requires an explicit operation to start another Hand, and reconnecting clients receive the latest complete view.

To preserve the declared reproducibility of automated selections after controller assignments change, accepted Bot actions retain their original Policy and ActionSelector identities, versions, configurations, and reconstructible evaluation and selection seeds in application-level provenance alongside the corresponding committed command. Poker replay still uses only the recorded ConcreteAction and never reruns a Strategy; returned distributions and scores remain derived analysis.
