# Separate Semantic and Durable Authority

CashGame is the semantic authority that validates and executes poker transitions, while PostgreSQL is the durable source of truth for committed Game Configuration, accepted commands, server-owned revisions, and processed network requests. The server serializes mutations per Table Session, applies each poker request to a temporary working CashGame, transactionally persists its accepted command, proposed server revisions, and idempotent result, and only after database commit promotes the working instance and publishes participant-safe updates. Cached CashGame instances are disposable and can be restored from the durable Table Session Record; their associated revisions are restored separately from the backend aggregate.

Create the temporary working instance with `committedGame.fork()` as defined in ADR-0011. The fork begins with the same poker facts and deterministic continuation but shares no mutable state with the committed cache. On rejection or confirmed persistence failure, discard it without changing the committed instance; only a confirmed durable commit permits promotion. An unknown commit outcome follows the recovery procedure below rather than being treated as a rollback. Server revisions and request metadata remain outside both CashGame instances.

M1 uses one FIFO mutation queue per Table Session in a single backend process; different sessions may progress concurrently. For an accepted poker mutation, the server proposes `pokerRevision + 1` and `sessionRevision + 1` without asking CashGame to track either counter. PostgreSQL commits the accepted command, both new revisions, and processed request together, with a unique `(tableSessionId, requestId)` safeguard. Promote the working game and both revision values together only after commit; a rejection or confirmed rollback advances neither committed revision. Multi-server coordination and database row locking are deferred.

Inside that queue, resolve requestId and its fingerprint first, returning a matching committed outcome without re-execution. For an unprocessed poker request, the server checks expectedPokerRevision against the latest committed poker revision before invoking a mutation on a temporary working CashGame. Application configuration requests similarly check expectedSessionRevision against the committed aggregate. Stale-request rejection and idempotency are server responsibilities; the engine still receives only its normal poker command arguments.

If confirmation of COMMIT is lost, the affected Table Session enters recovery and its mutation queue and Bot submissions pause until the backend resolves the outcome against durable state and reloads the confirmed aggregate. An initially absent processed-request row does not establish rollback while the transaction remains unresolved. A committed operation returns its stored outcome; a confirmed noncommit causes no automatic retry, and a human may submit a new requestId or Bot orchestration may freshly evaluate the still-current decision.
