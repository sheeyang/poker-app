# Route Computation Through One Server JobRunner

All Policy, Solver, and Research computation will pass through a server-managed JobRunner that owns execution, concurrency, cancellation, and failures within the single backend deployment. Jobs receive immutable inputs and declared configuration, return plain results, and never mutate a live authoritative or cached CashGame; this provides one execution boundary for different computational backends and keeps orchestration independent of implementation details. A job may construct and operate on isolated CashGame instances for simulation, Solver exploration, or private reconstruction using its permitted declared inputs, so those workflows reuse the same rules implementation without changing the active Table Session. This does not grant a Policy or participant-perspective Solver access to the live game's hidden facts or master seed. Orchestration captures the committed pokerRevision from the backend aggregate alongside the immutable participant-safe view, not from CashGame or ParticipantCashGame. That revision remains orchestration metadata rather than Policy input. Returned Bot work re-enters the Table Session mutation queue and is accepted only if its captured poker revision, Participant, Decision, Strategy assignment, seeds, and evaluation request identity remain current.

Result validity depends on its intended use: Bot actions require current poker state and controller identity, live displays require the current analysis request, and historical analysis requires its frozen inputs and matching request identity. Advancing the live game does not invalidate analysis of an immutable historical decision; a late result may still populate that decision's derived cache.

## Purpose-based scheduling

Use the same JobRunner for every job purpose. Callers declare a typed purpose, and one server-owned scheduling policy assigns its numeric priority; callers do not choose arbitrary priority numbers or own separate policies. Smaller numbers are dispatched first, and priority levels use numbers rather than word labels.

| Job purpose | Priority |
| --- | --- |
| Bot decision needed to advance play | 0 |
| Live Analysis or explicitly requested interactive analysis | 1 |
| Automatic post-action analysis or missing analyses for Hand or Table Session summaries | 2 |
| Bulk Research or simulation, when introduced | 3 |

M2 extends M1's existing bounded FIFO runner with FIFO ordering within each numeric priority. Each job's priority is fixed when submitted; priority selects which waiting job starts next without preempting running computation. Preserve bounded concurrency and queue capacity, submit summary work in small globally bounded batches across requests and tabs, and return an explicit capacity error when admission fails. M2 adds no reserved Bot slots or special fairness rule: continuous arrivals with smaller priority numbers may starve waiting work with larger numbers. This keeps the existing in-process execution model without a second runner or durable analysis queue.

The analysis module deduplicates matching queued/running analyses. An interactive request reuses matching work at its original numeric priority; M2 requires no promotion or duplicate execution. Connections own delivery and subscriptions, while scheduling, cache identity, deduplication, and retry behavior remain analysis responsibilities. Deduplication must not let one consumer abandoning a request cancel work still required by other consumers.

## Optional Live Analysis

The Trainer can enable Live Analysis before a human acts, using the same Reference Strategy and Policy system as review. Show its complete Choice distribution and its ActionSelector's concrete selected action when ready. While analysis is pending, show a loading state but leave legal human actions available: analysis must never block the human or alter CashGame. Turning Live Analysis off hides pre-action numerical results and skips unnecessary live evaluation unless another feature requires it; it does not affect Bot Strategies or poker progression. [ADR-0026](0026-retain-numerical-trainer-analysis-independently-of-gameplay.md) sets the default to off and requires an automatic nonblocking analysis request after every accepted human decision regardless of that setting. M2 uses matching cached results and queued/running job deduplication without requiring durable analysis obligations or guaranteed background completion; it validates the numerical pipeline through the Playground, while M3 owns product presentation and timing.

Each Policy request has an immutable identity distinguishing the DecisionId, Policy identity/version, complete Policy configuration, evaluation seed, and frozen input fingerprint. Complete Reference Strategy analysis also distinguishes the selector identity/version/configuration and selection seed. A returned result may update the live display only if the exact request is still current; the same DecisionId alone is insufficient when configurations change. Obsolete results never overwrite a newer request or another decision, but an otherwise valid late result may populate its original decision's derived analysis cache. Cancellation is an optional efficiency measure, not the correctness mechanism. Execution attempts are identified separately so a failed old attempt cannot replace progress or success from an explicit retry. HTTP get-or-start returns existing failures without restarting them; Retry operates only on failed work and preserves its inputs and seeds.

Table-scoped job results re-enter the Table Session queue for validity checks before orchestration uses them. Historical results remain keyed to frozen inputs rather than requiring the live poker revision to stay unchanged. Later review can analyze every recorded decision regardless of the Live Analysis setting during play, and users may select another complete Strategy or a deeper Policy-specific configuration without creating a separate live-analysis Policy or generic computation budget.

Bots differ from humans: the server must await valid Policy output and successful selection before submitting an action, while keeping the client responsive with a thinking state. Invalid, failed, or timed-out work produces no command or implicit action; Retry and Change Strategy follow ADR-0018.
