## M4 — Shared gameplay foundation

M4 establishes the shared lifecycle before elaborate animation work. The server is the source of truth for poker state and time. Animations represent game events; their completion never determines whether an action is valid. The requirements below define the planned M4 delivery.

### Scope and participant access

- Prove two real humans playing heads-up from separate devices over the internet. Use the current table UI with the controls needed for online play, connection status, countdowns, and explicit resume.
- Manually provision one private Table Session with two distinct secret participant links. Each link establishes an independently authorized identity controlling only its assigned Participant. Table Ownership does not grant participant credentials access to another Participant's private information.
- Use the same server turn lifecycle and action acceptance path for human and Bot controllers. Existing human-versus-Bot Trainer play remains supported and untimed by default; its subsequent Hands retain an explicit deal operation. Mixed human/Bot online seating and larger online tables remain deferred.
- Accounts, product invitation flows, lobbies, matchmaking, and broader online product features are future scope. They have no committed milestone number or priority relative to M6–M8 yet.

### Server scheduling and presentation contracts

- The server owns duration defaults, scheduling, and enforcement. Shared Contracts define the presentation phases and their timestamps, applicable street identifiers, action-window start and deadline, and next-Hand start time.
- Use bounded server-controlled presentation windows before opening the next turn and starting its action clock. The server accepts actions only within its authoritative turn lifecycle; clients cannot extend or open a turn by finishing an animation.
- Preserve atomic CashGame operations. Server schedules describe the transitions returned by those operations; animation steps are not additional poker commands.
- During normal betting, future streets, unrevealed opponent cards, burn identities, and deck order remain inaccessible through participant-facing responses. Once no betting decisions remain, the complete participant-safe resolved result may arrive together before its presentation finishes.
- For an all-in runout, build the presentation schedule from the remaining transitions: hole-card reveals, remaining board streets in order (flop, turn, river as applicable), payout, and the inter-hand pause. Each step uses server-owned duration settings and carries its phase, applicable street, and timestamps.
- Complete views remain the synchronization authority. Reconnect restores the latest authoritative view and current schedule; clients follow the timestamps and can skip elapsed motion without replaying missed events. Skipped animations, reduced motion, slow clients, and analysis completion never alter deadlines or Hand starts.
- Persist the active timing and schedule information needed for restart recovery. Preserve action deadlines across server restart and resolve expired decisions exactly once before accepting further actions. Recovery and repeated delivery must not duplicate timeout actions, payouts, or Hand starts.

### Eligibility, disconnects, and successive Hands

- An eligible participant has a funded seat, an active connection, and participation enabled.
- A mid-Hand disconnect leaves the participant in the current Hand, with their existing action deadline continuing normally. A missed action automatically checks when legal and otherwise folds. Subsequent decisions in that Hand still use the same turn lifecycle.
- A timeout marks the participant as sitting out after the current Hand, requiring explicit resume. If a participant is still disconnected when the Hand ends, also mark them as sitting out and exclude them from another Hand.
- Reconnection restores the latest authoritative view, including the current chip balance. Require explicit resume if the participant has been marked sitting out. Reconnection during the current Hand before a timeout permits normal continuation.
- Always settle payouts and preserve remaining chips. Never automatically rebuy.
- Automatically deal subsequent online Hands after the payout and inter-hand presentation windows, provided at least two eligible participants remain. Recheck eligibility when the countdown expires. If fewer than two remain, cancel the countdown and wait; when at least two become eligible again, announce a fresh next-Hand start time. Animation completion never triggers or delays dealing.

### Online Live Analysis and scoring

- Allow Live Analysis and normal numerical scoring during online play. Persist each Participant's own Reference Strategy and Live Analysis preferences, with participant-specific scores and summaries. One participant's study settings do not change the other's.
- Supply analysis only with participant-visible information from `ParticipantCashGame.getView()`. Scoring uses `getView({ at: { decisionId } })` for the historical snapshot at the original decision, together with the accepted action. Later streets, showdown reveals, and subsequent Hands must not contaminate those inputs.
- Enforce participant authorization across analysis capture, cached result reads, retry, summaries, and notifications. Analysis responses must not expose unrevealed opponent cards or future cards. Online participant credentials cannot access privileged completed-Hand inspection, hidden deck data, or another participant's private analysis.
- Analysis remains nonblocking: neither its computation nor feedback delays actions, deadlines, or automatic dealing.
- Treat timeout-generated checks and folds as human actions for normal Decision Scores, Action Rank Scores, and score averages. No separate action-origin tracking is required.

### Completion evidence and architecture follow-up

Demonstrate successive Hands with two real humans on separate devices over the internet using simple visuals and the existing UI. Verify server-controlled phase and action timing, all-in schedules, automatic dealing with eligibility rechecks, disconnect/reconnect and sit-out/resume behavior, chip preservation, and restart recovery without duplicate actions or deals. Automated checks must also cover independently authorized actions and analysis, historical snapshot visibility, timeout scoring, and clients that skip or miss animation phases.

The M4 extension ADR must explicitly revisit these existing policies:

- ADR-0018 currently lets human decisions wait for reconnection and requires explicit subsequent Hand starts. Timed online play introduces deadlines, timeout actions, and automatic successive Hands; Trainer remains untimed by default with explicit dealing.
- ADR-0026 stores Trainer preferences per Table Session for one owner. Online play requires participant-specific preferences, analysis authorization, scores, and summaries.
- ADR-0028 uses immediate complete-view rendering with optional local motion. M4 adds server-controlled presentation and action windows while preserving complete-view recovery and keeping animation completion out of action validity.

ADR-0012's atomic engine operations and ADR-0017's participant-safe projection and historical visibility boundaries remain requirements.
